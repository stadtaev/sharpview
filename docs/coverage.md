# Supported analysis and limits

This first increment targets restored SDK-style C# projects and solutions, hosted on .NET 10. It uses SDK MSBuild workspace loading, not Visual Studio. Configuration and target framework are recorded. One variant per project is analysed; an explicit framework is applied across the loaded input and must be declared by each selected project. Missing assets in any selected project currently abort loading. Workspace/compiler failures that still yield compilations become visible gaps. Opening/evaluating a project precedes the assets check; project tooling/source generators may execute. Sharpview never explicitly builds or restores input or edits its source.

Controller actions follow a documented convention: declared public instance ordinary nongeneric methods on nonabstract, nongeneric source types semantically deriving from ASP.NET Core `ControllerBase` or carrying `[Controller]`. Inherited `[NonController]`/`[NonAction]` exclusions are respected. Route/HTTP attribute type names are retained. Inherited action enumeration, controller discovery by naming alone, application-model conventions, endpoint reachability and minimal APIs are outside scope; recognised minimal-API registrations produce gaps. The CLI always prints these controller coverage limits.

Supported calls include normal invocations, explicit construction, source constructors, source property/event accessors, user-defined operators/conversions, reduced extension methods and separately owned local/lambda bodies. Interface and virtual bindings are boundaries, including virtual members with bodies; an explicit root may inspect its own declaration. Delegates, dynamic dispatch, function pointers and invalid operations remain boundaries. Top-level statements and field/property initialisers create scoped ownership gaps. Generated documents are included by default; exclusion produces evidence. Metadata-only bodies are normal static boundaries; exception origins within them are Unknown.

Explicit throws and throw expressions use semantic types. `throw new E()` has exact construction evidence; `throw e` has only its statically known type. Rethrows retain the original exception through a selected simple handler. Filters may accept, reject or throw and therefore stop that witness as Unknown. Complex handler flow, finally effects, iterator/enumeration/disposal/lock behavior, custom awaitables, async void and aliased/unobserved tasks remain outside supported propagation. Exceptions from constructors, getters and framework calls can be implicit; no inference of those implicit origins is attempted.

All branch calls are structural facts, regardless of feasibility. Catch-body calls are structural facts too; independently reached handler-origin throws are Unknown. A catch is never advertised as successful recovery. An action escape is scoped to this analysis model. Registration evidence from common ASP.NET Core exception handlers does not prove middleware order, environment conditions, invocation, response availability or complete boundary handling.

Architectural layers require explicit project/namespace prefix mappings. Distances describe static transitions from an action, not stack depth. Cycles and depth/work/output budgets are visible. Cancellation is propagated through load, extraction and traversal; a global output/work stop prevents claims of exhaustive enumeration.

The repository tests combine independently built snapshots, in-memory Roslyn compilations, a three-project Web API fixture and fresh CLI processes. They pin unrelated/incompatible catches, rethrow/replacement and subsequent interception, filters, await observation, dispatch boundaries, source ownership, cancellation and exact limits. Sample fixture reports are stored in `docs/samples`. Sharpview's own solution is only a loader smoke input; no external Web API analysis is claimed.
